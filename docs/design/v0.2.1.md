# superagent v0.2.1 — fix contract

Fixes for the seven findings in the Lead's adversarial review of v0.2. This file is the binding
spec for the fix workstreams. Do not change an interface here without the Lead's agreement.

## Findings and required behaviour

### 1. Failed dependency strands the run (Lead)
- `next` gains action `stuck T2 ...`: in phase `running`, after `launch`/`merge`/`wait` have had
  their chance, a planned ticket whose explicit `depends_on` entry is `failed` or `dropped` is stuck.
  `--json` action `stuck`. Printed line `stuck T2`.
- New command `superagent retarget <T> --depends-on <ids|none>` (orchestrator-only): only a `planned`
  ticket; replaces `depends_on` with the given ids (comma/space separated) or clears it for `none`.
  Validates: ids exist, no self, no duplicates, dependency not failed/dropped, dependency wave <=
  ticket wave, no dependency cycle. Appends event `ticket_retargeted { ticket, from, to }`.
- New command `superagent drop-ticket <T> --reason <text>` (orchestrator-only): only `planned`,
  `blocked` or `failed`; sets status `dropped`, appends `ticket_dropped { ticket, reason, from }`.
  Refuses running/ready/merged. This is how the orchestrator unblocks downstream tickets.
- `start-ticket` refusal for an unmet explicit dependency names the failed/dropped dependency and
  suggests `retarget`/`drop-ticket`.
- `skills/orchestrate/SKILL.md`: handle `stuck`; use retarget to point a ticket at its handback/fix
  replacement, or drop it; then call `next`.

### 2. audit misses commits on the integration branch (audit-dev)
- New hard check `integration commits`: `git rev-list --first-parent <base_sha>..<integration_branch>`
  must be exactly the shas recorded in this run's `merged` events (order-insensitive set). Any other
  commit is a rogue commit: name it (oneline) and fail, exit 3.
- The dirty working tree becomes a hard failure (`clean tree` check) instead of a warning; the
  current-branch check stays a warning.
- Append the new checks to the `audited` event as before.
- Tests: rogue commit created in the main checkout on the integration branch is caught and named;
  a clean run with recorded merges passes; a dirty tree fails; existing tests updated.
- Scope: `lib/commands/health.mjs`, `test/cli-health.test.mjs`.

### 3. met coverage is only a shape check (Lead)
- `superagent review` reads the frozen Charter (`readCharter` + `parseCharter`), takes `in_scope`,
  and requires every in-scope item (whitespace-normalized) to appear in exactly one of `met` or
  `unmet`. Missing -> validation error naming the item; in both -> error. Extra entries beyond the
  in-scope list are allowed (they are not coverage evidence).
- Tests updated: fixtures use Charter in-scope items; empty/missing coverage rejected.

### 4. Frontier can run two tickets owning the same paths (Lead)
- Plan validation: for any pair of tickets in different waves whose `owns` overlap, if the later
  (higher-wave) ticket declares `depends_on`, the earlier ticket must be in the later ticket's
  transitive dependency closure; otherwise error. (Tickets without explicit deps keep the wave
  barrier, which already serializes them.)
- Runtime: `isLaunchable` also refuses a ticket whose `owns` overlap a `running` or `ready` ticket;
  `next` never selects two overlapping tickets in one `launch` action; `start-ticket` refuses a
  ticket whose owns overlap a running/ready ticket, naming the holder.
- Tests: plan-time rejection with/without the dependency edge; runtime wait/merge ordering;
  start-ticket refusal.

### 5. Fix-wave instruction fails on frontier runs (Lead)
- `skills/orchestrate/SKILL.md`: fix and fidelity waves use **the highest wave in the run + 1**
  (read it from `superagent show --json`, `Math.max(...tickets.map(t => t.wave))`), not
  `current_wave + 1`; note it must also be above every merged wave.
- `add-ticket` wave errors suggest the next usable wave (`max(all ticket waves, merged waves,
  current_wave) + 1`).

### 6. Evals can't answer speed at equal accuracy (evals-dev)
Scope: `evals/**`, `test/evals.test.mjs`.
- Prompts pre-approve the proposal and tell the orchestrator to answer worker questions with the
  most conservative option (headless has no AskUserQuestion).
- Authentication pre-check before live runs: a minimal `claude -p "reply ok"` with the same config;
  on failure stop with a message naming login / `ANTHROPIC_API_KEY`.
- Config handling: by default `--live` uses the caller's real login/config; `--isolated-config` uses
  a throwaway `CLAUDE_CONFIG_DIR` (document that this needs `ANTHROPIC_API_KEY`). Never copy or
  modify the user's credentials.
- Accuracy: for every arm, run an independent acceptance check `evals/accept.mjs <repo>`: require a
  git repo with >= 1 commit; if `package.json` has `scripts.test` run `npm test`; else if a Makefile
  exists run `make test`; else fail "no test command". Record pass/fail + a short output tail.
- `--runs N` (default 1) repeats each arm; report per-arm wall-clock (min/median/max), exit codes,
  acceptance pass rate, and for superagent arms the run metrics from `metricsForRun` plus
  `human_interventions`. Write a JSON summary under `evals/results/` and print a table.
- Update `evals/README.md` honestly (live still needs verification; sample size guidance).
- Keep dry-run the default and test it.

### 7. Reviewer read isolation is only prompt-level (guard-dev)
Scope: `hooks/hooks.json`, `hooks/guard-read.mjs` (new), `hooks/guard-bash.mjs`, `lib/guard.mjs`,
`agents/fidelity-reviewer.md`, `test/guard.test.mjs`, `test/hooks.test.mjs`,
`test/guard-read.test.mjs` (new).
- New PreToolUse hook for `Read|Grep|Glob` -> `hooks/guard-read.mjs`. Only acts when
  `payload.agent_type === 'superagent:fidelity-reviewer'`; every other caller is allowed.
  For the reviewer, resolve the requested path (`Read`: `tool_input.file_path`; `Grep`/`Glob`:
  `tool_input.path`, default `payload.cwd`) and allow it only inside the run's `review_worktree`
  (realpath-aware, reusing `resolveReal`); deny the main checkout, `.superagent/` and any other path
  with: `Blocked: the fidelity reviewer may read only its review worktree.`
  Unreadable/missing state fails open with a stderr warning (like the other guards).
- `lib/guard.mjs` `decideBash`, when `reviewer` is true: deny any command containing `.superagent`
  unless every occurrence is `.superagent/drafts` (closes glob/relative tricks); deny
  `superagent show` combined with `--json` (also the `node .../superagent.mjs` form); keep the
  existing main-root denial. Applies even with no guarded run.
- `agents/fidelity-reviewer.md`: state that Read/Grep/Glob are hook-restricted to the review
  worktree and `show --json` is hook-denied, and that this is now enforced, not just requested.
- Tests: read hook allows non-reviewer and reviewer's own worktree paths, denies main-root,
  `.superagent/` and default-cwd reads; Grep/Glob path handling; Bash guard denies `.superagent`
  glob/relative forms and `show --json` (both flag orders and node form); existing guard tests stay
  green.
