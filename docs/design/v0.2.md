# superagent v0.2 — interface contract

This is the single source of truth for the v0.2 work. Every workstream implements against this
file. Do not change an interface here without the Lead's agreement; message the Lead instead.

Goal: raise **verified build speed** without lowering accuracy. See README and `docs/design/spec.md`.
v0.2 adds trust checks, concurrency-safe state, plan preflight, frontier scheduling, tiered model
selection, reviewer isolation, operational commands, docs and an eval harness.

## Conventions (do not change)

- Node >= 22 ESM (`.mjs`), no npm dependencies. Tests are `node --test test/`.
- Exit codes: 0 ok, 1 usage/validation, 2 state, 3 refusal/conflict (see `lib/errors.mjs`).
- Handlers get `(args, ctx)`; `ctx.resolveRun(args)` returns `{ root, run }`; `args.flags` /
  `args.positional` from `lib/cli.mjs`. A handler may set `handler.booleans = ['json']`.
- Every command group is a default-export object of `name -> handler`; the Lead wires it in
  `bin/superagent.mjs`. Do not edit `bin/superagent.mjs` (Lead owns it).
- State writes go through `lib/state.mjs` helpers. Never `git commit`, `git checkout`, `git add`,
  `git stash`, or otherwise write to git history: the Lead owns git. Read-only git is fine.
- Do not edit files outside your workstream's scope, and do not edit `test/helpers.mjs`.
  If you need a change elsewhere, message the Lead.
- Keep the existing 246 tests passing, and add tests for everything you add. Test files you own
  are listed per workstream below; other test files belong to other workstreams.

## 1. New commands

### `superagent doctor`

Runs environment and guard self-checks. Exit 0 when every check passes, 1 when any fails.
Output lines: `ok: <check>` / `FAIL: <check>: <detail>`, then one summary line.
Checks (a `warn:` line, not a failure, where noted):

1. Node major >= 22.
2. Plugin layout: `hooks/hooks.json`, `hooks/guard-files.mjs`, `hooks/guard-bash.mjs`,
   `bin/superagent` all exist; `bin/superagent` is executable.
3. `hooks.json` registers a PreToolUse matcher for `Write|Edit|MultiEdit|NotebookEdit` and one for
   `Bash`, each calling a guard script that exists.
4. Guard self-tests using the plugin's real `lib/guard.mjs`:
   - `decideFileWrite` denies a write to `<root>/.superagent/runs/x/charter.r1.md` (phase irrelevant);
   - `decideBash` denies `git push` for a synthetic guarded run (integration_branch set, phase
     running) with empty allowed_actions;
   - `decideBash` allows `git status`.
5. Inside a git repository: `mainRoot` resolves — warn, not fail, outside a repo.
6. An active run, when present, loads without error — warn, not fail, when there is none.

Implementation must be importable for tests: export `runDoctor({ pluginRoot, cwd })` returning
`{ ok: boolean, lines: string[] }`, and the CLI handler printing the lines and setting the exit code.
`pluginRoot` defaults to the directory containing `bin/` (derive from `import.meta.url`).

### `superagent audit [--run <id>]`

Integrity check of the main checkout against the approved run. Read-only. Exit 0 when clean,
3 when violated, 2 for a state error (e.g. no integration branch yet).

Checks:
1. The run has an integration branch and `base_sha`.
2. The base branch tip still equals `run.base_sha`: `git rev-parse <base_branch>`. On mismatch print
   every commit on `<base_branch>` not in `base_sha` (`git log --oneline <base_sha>..<base_branch>`)
   and fail with an explanation that a worker or command changed the base branch.
3. No unexpected commits on the base branch (covered by 2) and the main checkout's current branch is
   `run.integration_branch` (warn only; the orchestrator checks it out during runs).
4. `dirtyFiles(root)` is empty (warn only).
5. Guard self-test from `doctor` passes (warn only if plugin layout is missing).
Append event `audited` with `{ ok, checks: [{name, ok, detail?}] }` and print `audit ok` on success
or `audit FAILED` plus one line per failure.

### `superagent stats [--run <id>] [--json]`

Derived run metrics from `run.json`, tickets, reports and `events.jsonl` (read-only). Exit 0.
`--json` prints one JSON object, otherwise human lines. Fields (names are the JSON keys):
`id`, `title`, `phase`, `wave`, `parallelism`, `created_at`, `finished_at` (null when not done),
`duration_seconds` (now - created_at, or finished), `tickets_total`, `tickets_by_status`,
`tickets_by_origin`, `attempts` (sum), `blocked_events` (count of `ticket_reported` with
`status:"blocked"`), `merge_conflicts` (count of `merge_conflict` events), `merges`,
`verifications` (count of `verified`), `reviews`, `fix_waves_used`, `events_total`.
Use `loadEvents` (it throws on corrupt JSON; that is a state error, exit 2).

### `superagent next [--run <id>] [--json]`

Read-only. Prints **one action** for the orchestrator. Exit 0. `--json` prints
`{ action, tickets: [], detail }` where `tickets` are the relevant ticket ids (empty when none).

Action precedence (first match wins):
1. Phase `done`/`aborted`/`proposing`/`awaiting_approval`: `none`.
2. `run.merging_ticket` set: `merge-continue` (tickets `[merging_ticket]`).
3. Any ticket `status:"blocked"`: `ask` (ticket with the lowest numeric id).
4. Phase `verifying`: `verify`.
5. Phase `reviewing`: `review`.
6. Phase `running`:
   - Ready tickets (see Readiness) up to `run.parallelism` minus the number of `running` tickets:
     `launch` with those ids, lowest numeric first, at most the free slots.
   - Else any `status:"ready"` (finished, unmerged) ticket: `merge` with the lowest id.
   - Else any `status:"running"`: `wait`.
   - Else no open tickets (`planned`/`running`/`blocked`/`ready` absent) and no planned tickets:
     `advance` (the orchestrator runs `superagent next-wave`, which moves to `verifying`).
   - Otherwise: `none`.

**Readiness** (used by `next`): a ticket is launchable when status is `planned` and:
- every id in `ticket.depends_on` (default `[]`) has status `merged`; and
- if `depends_on` is empty, every ticket in a **lower wave** is `merged` (backwards compatible with
  waves); a ticket with explicit `depends_on` ignores lower-wave barriers but still respects its own
  edges.

`next` never changes state. Human output is exactly one line: `launch T3 T4`, `merge T2`, `ask T5`,
`verify`, `review`, `advance`, `wait`, `merge-continue T2`, or `none`.

### `superagent review-setup [--run <id>]` / `superagent review-close [--run <id>]`

Isolate the fidelity reviewer from run state by giving it a checkout that does not contain
`.superagent/` (untracked files are not copied into a worktree).

`review-setup`: requires phase `reviewing`. Creates a detached worktree of `run.integration_branch`
at `join(os.tmpdir(), "superagent-review-<run id>-<random>")` via
`git worktree add --detach <path> <integration_branch>`. Stores the path in `run.review_worktree`,
saves the run, appends event `review_worktree_created` with the path, and prints the path alone on
stdout. Idempotent: if `run.review_worktree` is set and the directory exists, print it again.
`review-close`: removes the worktree (`git worktree remove --force <path>`), clears
`run.review_worktree`, appends `review_worktree_removed`, prints `review worktree removed`.
The reviewer writes its JSON to `<worktree>/.superagent/drafts/<run id>/review.json`; the
orchestrator records it from the main checkout with `superagent review --file <absolute path>`.
`review` must accept absolute `--file` paths (it uses `resolve(ctx.cwd, file)`, which already does).

### `superagent ruling --text <text> [--ticket <T>]`

Appends event `ruling` `{ text, ticket? }` to the active run's event log; prints `ruling recorded`.
Exit 1 when `--text` is missing or empty. Orchestrator-only (it is not in `WORKER_COMMANDS`).

### `superagent context [--run <id>]`

Prints a compact resume brief (read-only, exit 0) for the orchestrator after compaction:
```
run: <id> · <title>
phase: <phase> · wave: <current_wave or -> · parallelism: <n>
branch: <integration_branch> (base <base_branch>)
tickets: <total> (<n merged, n running, n planned, n blocked, n failed, n dropped>)
<one line per ticket not merged/dropped>: <id> <status> wave <w> · <title>
blocked: <id>: <question text>        (only when a blocked ticket exists, lowest id first)
fidelity: <n unmet, n extras, n contradictions> (latest review, or none)
next: <the `next` action line>
```
Exit 2 when there is no active run.

## 2. Plan schema additions (`lib/plan.mjs`, `lib/commands/plan.mjs`)

`Plan` gains top-level `shared_files?: string[]` and per-ticket `depends_on?: string[]` and
`model?: string`.

Validation additions, all returned as one-line errors like the existing ones:
- `shared_files`: array of strings; each `normalizeRel` non-null; no globs (`*`, `?`). Duplicates are
  an error. Every shared file must be owned by at least one `scaffold` or `contracts` ticket
  (`ownsPath`), and **no `work` or `fix` ticket may own it**. With `project.kind:"new"`, at least one
  scaffold ticket must exist (already enforced).
- `depends_on`: array of ticket ids; each must exist in the plan; no self-reference; no duplicate;
  no cycles (report `T1: depends_on cycle: T1 -> T2 -> T1`); `dep.wave <= ticket.wave` (a dependency
  in a later wave is an error). A ticket that depends on a `contracts` ticket must be in a later wave
  (already implied). `wave` stays required and authoritative for display.
- `model`: non-empty string when present. Stored on the ticket as `model` (null when absent).
- `propose` stores `run.shared_files` (normalized, default `[]`) and renders a `Shared files:` section
  in the proposal (after Contracts, one line per file) and in `renderProposal`.
- `add-ticket` (in `lib/commands/ticket.mjs`) accepts the same `depends_on`/`model` fields; it
  reuses `validatePlan`, so the rules apply automatically. Store `depends_on` and `model` on the
  ticket (defaults `[]` and `null`).
- New ticket fields: `model: string|null`, `depends_on: string[]`. Existing run/ticket JSON fixtures
  without them must keep working: read with `?? []` / `?? null` where the code touches them.

`lib/commands/next.mjs` implements the `next` command above; it may import helpers from
`lib/plan.mjs` / `lib/state.mjs`.

## 3. State additions (`lib/state.mjs`, `lib/commands/ticket.mjs`)

- `Run` gains `shared_files: string[]` and `review_worktree: string|null`. `createRun` sets
  `shared_files: []` and `review_worktree: null`.
- Concurrency-safe ticket updates. Add to `lib/state.mjs`:
  `updateTicket(root, runId, ticketId, mutate)` — takes a per-ticket lock, loads the ticket, calls
  `mutate(ticket)` (may throw to abort), writes it atomically, returns the ticket. Lock file:
  `<run dir>/tickets/<T>.lock`, created with `openSync(file, 'wx')`, retried up to ~5 s at ~20 ms,
  removed in `finally`; a lock older than 30 s is stale and is removed. Export a test hook or take
  an options object so the lock timeout can be shortened in tests.
  Refactor `lib/commands/ticket.mjs` so `start-ticket`, `set-agent`, `mark-failed`, `claim`, `report`
  and `answer` read-check-mutate-write **inside** `updateTicket` (the status/phase checks move into
  the mutator; errors still map to the existing exit codes/messages). Do not lose events: append the
  event after the update succeeds.
- `lib/commands/ticket.mjs` `brief` gains a `## Project context` section: when
  `<drafts>/<run id>/context.md` exists (orchestrator-written, see prompts), include its content
  after `Checks`; mention it is read-only context, never requirements above the Charter.
- `lib/commands/meta.mjs` implements `ruling` and `context` (Lead creates the stub).

## 4. Review schema + reviewer isolation (`lib/commands/review.mjs`, `lib/guard.mjs`)

- `Review` gains a required `met` array of `{ item, evidence }` (non-empty strings), alongside
  `unmet`, `extras`, `contradictions`. `superagent review` validates and stores it.
- `review-setup` / `review-close` are implemented in `lib/commands/review.mjs`.
- `lib/guard.mjs` `decideBash` gains ctx field `reviewer` (boolean) and `mainRoot` (string, optional):
  when `ctx.reviewer` is true, deny any command that mentions the main root path or
  `.superagent/runs` (substring match, case-insensitive), with reason
  `Blocked: the fidelity reviewer works only in its review worktree and must not read run state.`
  This applies even when the run is not guarded. Add unit tests.
- `hooks/guard-bash.mjs` passes `reviewer: payload.agent_type === 'superagent:fidelity-reviewer'`
  and `mainRoot: root`.
- `agents/fidelity-reviewer.md`: work in the path printed by `superagent review-setup`; run
  `superagent show --run`/`--charter` and `git diff <base_sha>..<integration_branch>` from the main
  checkout only to read them, then do the judging in the review worktree; write the JSON to
  `<worktree>/.superagent/drafts/<run id>/review.json`; the report must cover every in-scope Charter
  item in `met` (with evidence) or `unmet`; final message is the JSON only.
